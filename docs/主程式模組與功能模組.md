# 主程式模組與功能模組

本文件是「主程式＋功能模組」架構的**研究結論與設計規格**：現況分析、模組契約（manifest）、
獨立開發與安裝啟用流程、以及功能模組掛勾主程式兩大設施（系統公告、行事曆）的契約。
資料層細節仍以 `資料模型.md` 為準，Firestore 讀取以 `資料庫讀取規範.md` 為準。

## 1. 術語對照

| 本文件用語 | 註冊表欄位 | 意義 | 例 |
|---|---|---|---|
| **主程式模組** | `kind: "builtin"` | 隨主程式提供、一律啟用，無法停用 | 帳號管理、名冊、系統公告、行事曆、統計儀表板 |
| **功能模組** | `kind: "optional"` | 獨立開發、發表、由主程式安裝後，超級管理員決定啟用與否 | 空間預約、模擬考報名、自主學習、學習歷程、線上點名 |

對照現有程式碼：

- 產品層級註冊表 `src/types/feature-modules.ts:228`（`FEATURE_MODULES`），分類欄位
  `kind: "builtin" | "optional"`（同檔 `:36`）——**本文件的術語就是它的中文化，不另造新欄位**。
- 管理端權限單位 `src/types/modules.ts:53`（`MODULES`）是另一張表，由名冊「指定功能模組」
  指派、`requireAdminModule` 守門；主程式模組的管理卡由它派生，**兩張表不可混用**
  （各檔頭註解已規範）。
- 行政語意：**「安裝」＝把模組程式碼納入建置並部署；「啟用」＝運行時開關**
  （`settings/system.featureModulesEnabled`）。兩者不可混淆，見第 5 節。

## 2. 現況分析

### 2.1 三分現狀

**（一）主程式模組：是真的，但不獨立。**
每個 builtin 模組都有頁面與 API，但程式碼散在主程式各處（如 `src/app/admin/announcements/`、
`src/app/api/admin/announcements/`）。新增一個模組要手改 6–8 處核心檔——實例 commit
`359e835`（公告模組）動了 20 個檔，包含兩張註冊表（`types/modules.ts`、
`types/feature-modules.ts`）、`components/ModuleIcon.tsx:7`（`ICON_PATHS` 表）、
`components/RoleHome.tsx`（首頁卡片）、`lib/rate-limit.ts:130`（`RATE` 表）、
`lib/audit.ts:4`（`ActivityAction` 聯集）等硬編碼。

**（二）功能模組：全是佔位，零程式碼。**
5 個 optional 模組（`spaceBooking`、`examRegistration`、`selfLearning`、
`learningPortfolio`、`attendance`）全部 `status: "planned"` 且 `href: ""`
（`src/types/feature-modules.ts:171-221`），只存在於註冊表一列，無頁、無 API、無資料集合。
`calendar` 雖歸 builtin，但同樣是 `planned` 佔位（同檔 `:162-170`），
全 repo 無任何行事曆程式碼。

**（三）啟用機制：管線是真的，但總開關從未控過東西。**
管理頁 `/admin/modules`（`src/app/admin/modules/page.tsx:403-404` 依 `kind` 分兩張表）、
`PATCH /api/admin/feature-modules`（`src/app/api/admin/feature-modules/route.ts:54`，
僅超級管理員 `:71`、稽核紀錄）、`settings/system.featureModulesEnabled` 與
`featureModuleRoles` 兩欄位（覆寫時保留，`src/app/api/settings/route.ts:172-175`）皆就緒。
但可切換條件＝「選用**且**已上線」（`src/types/feature-modules.ts:251`），
現無任何 optional 是 `live` → **總開關是先蓋好、尚無對象的空開關**
（「模組×身分顯示」開關則有在管 builtin 模組）。

**結論：「功能模組獨立開發 → 發表 → 安裝 → 啟用」這條線，至今從未完整跑通過一次。**

### 2.3 技術限制（決策前提）

- Vercel 部署＋Next.js App Router，**路由是建置期由檔案系統決定**——運行時無法新增後端
  路由或安裝第三方程式碼。
- 因此定案：**安裝＝納入建置＋自動部署**（Git push → Vercel 自動 build），
  **啟用＝runtime 開關**（沿用現有機制）。真正的「不重部署即安裝」需要前端微模組＋
  外部 API，須放寬 CSP、放棄 server-only 資料存取，複雜度與風險不成比例，不採用。

### 2.4 缺口清單（待補）

1. 無模組目錄約定與 manifest → 新增模組要手改多個核心檔（2.1 之一）。
2. 無安裝語意與安裝清單 → 無流程可循。
3. 啟用管線無對象（2.1 之三）。
4. 跨模組掛勾只有公告一條，且未升格為正式契約；行事曆掛勾完全不存在（第 6 節）。

## 3. 模組契約設計

### 3.1 目錄約定

每個模組一個資料夾，**只對自己的資料夾負責**：

```
src/modules/<模組代碼>/
├── module.json        # manifest：模組契約的唯一註冊來源
├── README.md          # 模組說明、開發者、版本、安裝後的設定方式
├── admin/             # 管理端頁面（若有）
├── api/               # API route handler（若有）
├── components/        # 模組專屬元件
├── lib/               # 模組專屬伺服器邏輯（server-only）
└── types/             # 模組專屬資料模型
```

- `<模組代碼>` ＝ manifest 的 `value`，全域唯一，也是啟用狀態欄位
  `featureModulesEnabled` 的鍵。
- 模組可 import 主程式公開面（3.3），**不可**反向被主程式核心檔 import（除自動產生的註冊表）。
- **實體路徑＝manifest `routes` 路徑原樣鏡像在模組根目錄**（P2 掛載約定）：
  `/admin/space-booking` → `src/modules/spaceBooking/admin/space-booking/page.tsx`（可選 `layout.tsx`）；
  `/api/admin/space-booking` → `src/modules/spaceBooking/api/admin/space-booking/route.ts`。
  掃描器只在實體存在時產生轉接檔——manifest 可先註冊（`status: "building"`）後實作，
  實體尚未存在＝該路徑 404（尚未掛載），實體一出現即自動掛載。

### 3.2 `module.json` 欄位

前段＝現有 `FeatureModuleMeta`（`src/types/feature-modules.ts:70-86`）原樣搬出，
後段＝本次新增的掛載宣告：

```jsonc
{
  // —— 既有 FeatureModuleMeta ——
  "value": "spaceBooking",
  "label": "學校空間預約模組",
  "kind": "optional",              // optional＝功能模組；主程式模組不放本目錄
  "status": "planned",             // planned → building → live（live 才可啟用）
  "description": "教室、場地等學校空間的預約、審核與使用紀錄。",
  "href": "/admin/space-booking",  // ""＝尚未建頁
  "author": { "author": "", "authorUrl": "", "version": "1.0", "releasedAt": "" },
  "provides": { "student": false, "parent": false, "staff": true, "admin": true },

  // —— 新增：掛載宣告 ——
  "routes": [                      // 頁面與 API 掛載點（P2 產生薄轉接檔用）
    { "kind": "page",  "path": "/admin/space-booking" },
    { "kind": "api",   "path": "/api/admin/space-booking" }
  ],
  "permission": {                  // 管理端權限歸屬
    "mode": "new",                 // "new"＝新增一個 assignable 權限單位
    "value": "spaceBooking",       // 或 "reuse": "classes"（併入既有權限單位）
    "category": "校務資料"
  },
  "icon": "spaceBooking",          // ModuleIcon ICON_PATHS 的鍵（缺省用 fallback）
  "rateLimits": [                  // 模組自有的限流桶（名稱須加模組前綴）
    { "key": "SPACE_BOOKING_GET",  "limit": 60, "windowMs": 60000 },
    { "key": "SPACE_BOOKING_MUTATE", "limit": 20, "windowMs": 60000 }
  ],
  "auditActions": ["space_booking_updated", "space_booking_approved"],
  "dataCollections": ["spaceBookings"],   // 用到的 Firestore collections（供讀取規範檢查）
  "hooks": ["announcements"]        // 掛勾的主程式模組（第 6 節）
}
```

規則：

1. `value` 全域唯一；與註冊表重複時 build 期直接報錯（fail-fast）。
2. **manifest 是唯一註冊來源**——不再手刻 `RAW_FEATURE_MODULES`（該列改為自動產生，
   見 3.4-P1）。
3. `status` 只能由模組作者在 manifest 改；`planned`/`building` 無入口、不可啟用
   （既有規則不變，`src/types/feature-modules.ts:251`）。
4. `rateLimits.key`、`auditActions` 必須帶模組代碼前綴，避免撞名。

## 4. 獨立開發流程

1. **開分支** `module/<value>`，於 `src/modules/<value>/` 自治開發；
   主程式核心檔凍結（只改自己模組需要的公開面時，另開 commit 說明）。
2. **先註冊、後實作**：manifest 先以 `status: "building"` 註冊——
   `/admin/modules` 會顯示「開發中」且無入口，不影響現行運作。
3. **本機驗收**：`npm run lint`（eslint + tsc）→ `npm run dev` 手測四身分可見性與權限不足路徑。
4. **對照第 3.3 節禁止事項與 `資料庫讀取規範.md` 末尾檢查清單逐項核對。**
5. **發表**＝合併 `main` → push（Vercel 自動部署）→ `status` 改 `live`。
   依 `AGENTS.md` 流程：lint → `npm run version:bump` → commit（結尾附
   「版本號更新至 0.xxx」）→ push。

## 5. 安裝與啟用流程

```
開發者                     主程式建置                     超級管理員
──────                    ─────────                     ──────────
寫模組（分支）
  → lint / version:bump
  → commit + push  ─────→  Vercel 自動 build
                             （掃 manifest、產生註冊表
                              與轉接檔、打進 bundle）
                           上線，但 featureModulesEnabled
                           查無此鍵 ＝ 未啟用（fail-safe）
                                                        → /admin/modules
                                                        → 開總開關
                                                        → 選模組×身分顯示
                                                        → 首頁卡片即時出現
                                        ↑
                              settings/system 變更 → 快取失效
                              → 稽核 feature_module_updated
```

- **安裝的原子單位是「合併＋部署」**：沒有「裝一半」狀態；失敗就 revert 再部署。
- **啟用是完全的 runtime 行為**：不重新部署、即時生效（30 秒快取上限）。
- **停用**＝反向操作；模組程式碼仍在 bundle，但無入口、首頁無卡片（API 攔截見 P4）。
- 日後可選：管理頁「安裝市集」→ 寫安裝清單 → 觸發 CI 部署（P3 之上加一層，契約不變）。

## 6. 跨模組掛勾契約

功能模組有兩類輸出須回流主程式設施：**公告資訊 → 系統公告**、**行程提醒 → 行事曆**。
兩條掛勾都遵守同一組總則：

1. **只寫該設施自己的集合**，不得自開平行集合。
2. **`sourceModule` 必填**（＝功能模組的 `value`），`sourceRef` 選填（該模組資料 id）。
3. **受眾必須明確**（roles ＋必要時 classCodes），不可無界。
4. **寫入成功後由掛勾函式內建清快取**，呼叫端不得自行繞過。
5. 掛勾是**伺服器端到伺服器端**的函式呼叫（不走 HTTP），故不經限流；
   觸發它的 API 必須有自己的 `RATE` 桶與 `requireAdminModule`／`requireRole` 守門。

### 6.1 掛勾 A：公告資訊 → 系統公告（已存在，升格為契約）

**介面**：`publishFromModule(input)`（`src/lib/announcements.ts:106`；
輸入型別 `PublishFromModuleInput` 同檔 `:85-100`）。

```ts
const { id } = await publishFromModule({
  sourceModule: "spaceBooking",        // 必填：自己的模組代碼
  sourceRef: booking.id,               // 選填：來源資料 id（如預約單號）
  title: "場地預約成功：視聽教室 A",
  body: "您預約的時段為 10/20 14:00–16:00…",
  authorUid, authorName, authorRole,   // 觸發當下的操作者
  audience: { roles: ["staff"], classCodes: [] },  // 必須明確
  publishAt, expireAt, pinned,         // 可選
});
```

**契約條文**（原 `src/lib/announcements.ts:36-47` 檔頭四條協議升格）：

1. 只寫 `announcements` 集合；模組**不得**建立任何平行公告集合。
2. `sourceModule` 必填，非公告模組自己發文時不可為 `"announcements"`；
   管理端清單會顯示 `[sourceModule]` 標籤（`src/app/admin/announcements/page.tsx:730-731`）。
3. 受眾必須明確：非公開時 `roles` 至少一個；`classCodes` 空陣列＝不限班級。
4. 校驗與快取失效**內建**——`validateAnnouncementInput`
   （`src/types/announcements.ts:343`）失敗即拋錯、成功即
   `invalidateAnnouncementsCache()`（`src/lib/announcements.ts:151`）。
5. 讀取端零負擔：公告收件匣／顯示位置的過濾下推與快取已由公告模組負責
   （`src/lib/announcements.ts:259,329`），掛勾方**只需寫入**。
6. **現況限制（實作時須知）**：本介面只有「發佈」，**沒有跨模組的更新/撤回**——
   公告發出後若來源資料取消，掛勾方須自行以管理 API 撤回，或等待 P5 擴充
   （見下）。功能模組若需要「取消即撤回」語意，請改用掛勾 B 的覆寫更新（6.2-3），
   或於 manifest 的 `hooks` 宣告同時需求，另提擴充。

**P5（候選擴充，未排程）**：`updateFromModule({ sourceModule, sourceRef, ... })`——
以 `sourceModule+sourceRef` 定位並更新/封存，讓「行程取消 → 公告同步下架」可行。

### 6.2 掛勾 B：行程提醒 → 行事曆（零程式碼，本節為契約設計）

**現況**：`calendar` 只有註冊表一列（`src/types/feature-modules.ts:162-170`，
builtin + planned + 空 href），無集合、無型別、無頁面。現有「提醒」只有公告個人提醒
（`announcementReminders`，`src/types/announcements.ts:16`，**非推播、開啟頁面才更新**，
`資料模型.md:109`）。**本節只定契約，行事曆模組本體（頁面/API）另期實作。**

#### (1) 資料模型：`calendarEvents` 集合

**刻意不放 `settings/*`**——系統設定是整份覆寫（`src/app/api/settings/route.ts:172-175`
僅保留固定欄位），行程資料混入會被抹掉；同 `announcements`、`settings/school` 的既有決策。

```ts
interface CalendarEventRecord {
  id: string;
  title: string;                 // ≤ 120 字
  description?: string;          // ≤ 2000 字
  location?: string;             // ≤ 120 字
  startAt: number;               // epoch ms
  endAt?: number;                // epoch ms；缺省＝單點事件
  allDayDate?: string;           // "YYYY-MM-DD"；全天事件用（與 startAt 二選一）
  sourceModule: string;          // 必填：來源模組代碼；行事曆自己建＝"calendar"
  sourceRef?: string;            // 來源資料 id（如預約單號）
  audience: {                    // 同公告受眾形狀
    roles: UserRole[];           // 至少一個（閱讀權限「無」時由系統補為四身分）
    classCodes: string[];        // 空陣列或含 "*"＝不限班級
  };
  isPublic: boolean;             // 閱讀權限「無」＝公開（不需登入可讀；與身分選項互斥）
  status: "active" | "cancelled";// 取消＝保留文件、不顯示（供對帳）
  createdBy: { uid: string; name: string; role: UserRole };
  academicYear?: number;
  semester?: 1 | 2;
  createdAt: number;
  updatedAt: number;
}
```

#### (2) 寫入介面：`publishScheduleFromModule()`

比照 `publishFromModule` 的形狀（`src/lib/announcements.ts:106`），
但**多出覆寫更新語意**——行程必然會改期/取消，這是與掛勾 A 最大的差異：

```ts
// 建立；同 sourceModule + sourceRef 再呼叫＝覆寫更新（upsert）
const { id, updated } = await publishScheduleFromModule({
  sourceModule: "spaceBooking",   // 必填
  sourceRef: booking.id,          // 強烈建議填：改期/取消靠它定位
  title, startAt, endAt, location,
  audience: { roles, classCodes },// 必填、明確
  status: "active",               // 取消時傳 "cancelled"
});
```

契約條文：

1. 只寫 `calendarEvents` 集合；校驗失敗拋錯（title 非空、時間合法、閱讀權限非空——「無」＝`isPublic` 屬合法）。
2. `sourceModule` 必填；**有 `sourceRef` 時以 `sourceModule+sourceRef` 定位**：
   存在→覆寫欄位（`updatedAt` 遞增），不存在→新建。無 `sourceRef` 每次皆新建。
3. `status: "cancelled"` **保留文件**（不刪除），供來源模組對帳與避免殘留個人提醒。
4. 寫入後內建 `invalidateCalendarCache()`（清 `calendar:` 前綴讀快取，形狀同
   `src/lib/announcements.ts:77-83`）。
5. 取消/過期事件**不回給任何讀取端**（同公告「到期自動隱藏」原則）。

#### (3) 個人行程提醒（鈴鐺）

沿用公告個人提醒的既定模式（**非推播**，開啟頁面才更新）：

- 集合 `calendarReminders`，**doc id ＝ `{eventId}_{uid}`**
  （同 `announcementReminders` 形狀，`src/types/announcements.ts:15-16`）。
- 使用者於行事曆列表切換「提醒我」→ toggle 寫入；再次點擊刪除。
- 讀取時逐筆驗證事件仍 `active` 且在未來、受眾涵蓋該使用者身分＋班級，
  否則不回（同 `src/lib/announcements.ts:491` `listMyReminders` 的做法：
  讀提醒 → `getAll` 批次讀事件 → 記憶體過濾）。
- 展示面：首頁鈴鐺（可與公告鈴鐺併列或合併計數，實作時定案）＋行事曆頁內。

#### (4) 讀取契約（過濾下推＋快取）

依 `資料庫讀取規範.md` 鐵律 2/3/6：

- **查詢條件全下推**：`status == "active"`（或缺省＋記憶體過濾）＋
  `audienceRoles array-contains role` ＋ 時間範圍（`startAt >=` 從今日零時）；
  班級、取消事件在記憶體過濾（量級同公告，避免複合索引）。
- **快取**：`cachedRead("calendar:<role>:<classCode>:<範圍>", 15_000, ...)`
  （同 `src/lib/announcements.ts:51` 的 15 秒 TTL 模式），
  寫入後由 `invalidateCalendarCache()` 清前綴。
- 跨實例上限＝TTL；這是既定取捨（`src/lib/read-cache.ts:17-19` 註解已說明）。

#### (5) 實作時機與註冊表關係

- 本契約**先行於實作**：行事曆模組動工時，依第 6 節總則建 `src/lib/calendar.ts`
  （server-only，比照 `src/lib/announcements.ts`），再把 `calendar` 的 `status`
  改 `live`、補 `href`。
- 在那之前 `calendar` 保持 `planned`：**無入口、不可啟用**（既有規則
  `src/types/feature-modules.ts:251`），功能模組的行程寫入也**不應早於行事曆上線**
  （寫了沒人看，且違反而 2.1 空開關問題）。
- 權限：`calendar` 為 builtin（主程式模組），一律啟用；四身分顯示沿用
  `featureModuleRoles` 機制，`provides` 由模組作者在註冊表定案。

## 7. 相容性檢查清單

實作任一模組或掛勾後，逐項核對：

1. **Firestore 讀取六鐵律**（`資料庫讀取規範.md`）：過濾下推、精準查詢、禁 N+1、
   同請求復用、快取＋寫後失效；對照文末「失效鉤子清單」補掛鉤。
2. **fail-safe 一律朝「關」**：啟用欄位缺＝未啟用；`provides=false` 強制不顯示；
   頁面/API 閘門 fail-closed。
3. **超級管理員 bypass** 只在「可見性」層（`src/types/feature-modules.ts:320`），
   不繞過資料寫入驗證。
4. **`settings/system` 覆寫保留** `featureModulesEnabled`、`featureModuleRoles`
   （`src/app/api/settings/route.ts:172-175`）——新增同類欄位時須一併加入保留清單。
5. **Next.js 版本注意**：動程式碼前先讀 `node_modules/next/dist/docs/`（`AGENTS.md`）；
   路由保護在 `src/proxy.ts`（非 middleware.ts）。
6. **CSP 無需為模組變更**（`src/proxy.ts:19-49`）：模組走同源路由，不引入新外來源。
7. **交付流程**：`npm run lint` → `npm run version:bump` → commit
   （結尾「版本號更新至 0.xxx」）→ `git push`（＝自動部署）。
