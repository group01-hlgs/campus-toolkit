# 資料讀取省流（剩餘 Phase 路線圖）

本文件追蹤「節省 Firestore 讀取量」專案的**剩餘階段**與狀態。
讀取怎麼寫、鐵律與檢查清單以 `docs/資料庫讀取規範.md` 為唯一規格來源；
本文只記路線（做什麼、為什麼、做到哪裡），兩者衝突時以規範為準。

起因：926 帳號／925 名冊的部署，下午管理各功能進 4～5 次就把 Spark 免費額度
**50,000 讀取／日** 的 1/5 燒掉；診斷大頭是三張管理端清單（名冊 ≈1,850 讀、
帳號工作表 ≈1,852、班級總覽 ≈927 的冷載）與每請求驗證基線 2 讀。

## 二、剩餘 Phase

| Phase | 內容 | 預期收益 | 風險 | 狀態 |
|---|---|---|---|---|
| 4 | school 四個設定 GET 統一 `setting-doc` 快取 | 每請求省 1～2 讀 | 低 | ✅ 已完成（0.312） |
| 5 | `verifySession` 使用者／名冊條目短 TTL 快取 | **每個受保護請求省 2 讀**（最大宗） | 中（權限時效） | ⬜ 未開始 |
| 6 | activity 稽核分頁快取 | 每請求省 50～200 讀（瀏覽時） | 低（晚幾秒可接受） | ⬜ 未開始（可選） |
| 7 | 部署觀測與規範回填 | 驗收專案成效 | 無 | ⬜ 未開始 |

### Phase 4：school 四個設定 GET 統一 `setting-doc` 快取 ✅

- **現況成本**：`school/profile` ≈3 讀、`school/org` ≈3、`school/codes` ≈3、
  `school/classes` ≈4（驗證基線 2 ＋ 設定文件 1～2 點查）。
- **問題**：同一份 `settings/schoolProfile` 在 `api/admin/classes` 已有
  `cachedRead("setting-doc:…", 30s)` 快取，`api/admin/school/*` 卻每次直讀，
  同文件重複計費。
- **動作**：
  1. `read-cache.ts` 加 `cachedSettingDoc(docId, load)`（key＝`setting-doc:<docId>`、
     TTL 30 秒）與 `SETTING_DOC_TTL_MS`，`api/admin/classes` 與四個 school GET
     全部改走同一 helper（key 同源才會互相命中）。
  2. `school/classes` 的 GET 讀 context 改走快取；**PUT 的驗證 context 維持
     直讀新鮮**（超級管理員改完學制馬上年段班級，不可驗在舊資料上）。
- **失效**：四個 PUT 皆已呼叫 `invalidateAdminListCache()`（同實例立即清、
  跨實例上限＝TTL 30 秒），鉤子現成、正確性風險近 0。
- **驗收**：`npm run lint` 通過；30 秒內重複進出四個設定頁，設定文件 0 讀。

### Phase 5：`verifySession` 使用者／名冊條目短 TTL 快取 ⬜

- **現況成本**：每個受保護請求固定 **2 讀**——`dal.ts` 使用者文件點查＋
  當期名冊條目點查；設定文件已由 `readSystemDoc` 30 秒共用吸收（0～1），
  `keepalive` 已是 0 讀。這是全站最大宗、且無法用「少進頁」避免的讀取。
- **收益**：一天數百～數千個 API 請求 × 2 讀，是壓過免費額度的主力。
- **設計紅線（動手前先寫設計稿確認）**：
  1. **TTL 只能 5～10 秒**——這是權限判定，不是清單；絕不抄清單的 10 分鐘。
  2. key 綁 `uid`（＋必要欄位如 `tokenVersion`），命中條件須涵蓋
     「檔案存在／不存在」（不存在也要快取，否則孤兒查詢照樣打）。
  3. **失效鉤子逐一列點**：帳號停用／改權／改 email／2FA（`api/admin/accounts`、
     `api/account`、`api/account/two-factor`）、名冊條目增刪（`api/admin/roster*`）、
     登入成功後的 `tokenVersion` 寫入（`api/auth/login`）、登出撤銷。
     可考慮 session key 直接綁 `cacheEpoch`——管理端變更自動全失效，
     代價是「任何管理端寫入」都會重讀驗證（仍遠比每請求 2 讀便宜）。
  4. jti 撤銷與登出檢查**維持不變**（本來就在快取外）。
  5. **可接受窗口必須寫進規範第五節**：「停用帳號／移除身分最多 N 秒後
     才全面生效」，上線前與 owner 確認 N。
- **風險**：中——快取過期策略錯＝權限漏洞。先讀 `dal.ts` 全部權限分支、
  列出所有改變權限判定輸入的寫入路徑，再實作。
- **驗收**：lint 通過；停用帳號在 TTL 內生效；受保護請求的驗證讀數下降
  （Firebase Console 對照）。

### Phase 6：activity 稽核分頁快取 ⬜（可選，排 Phase 5 之後）

- **現況成本**：`api/admin/activity` 每請求 `orderBy(timestamp desc).limit(N)`，
  預設 N=50（≈50 讀）、上限 200；驗證基線另 2 讀。
- **判斷**：稽核 log 高頻新增、瀏覽低頻且已限流——收益中等、不是爆點。
  若要做：key 含 `limit`＋分頁游標、TTL 5～10 秒、`logActivity()` 後
  `invalidateReadCache()`；正確性要求「晚幾秒看到新紀錄」可接受才動。
- **驗收**：lint 通過；寫入稽核後 10 秒內頁面看得到該筆。

### Phase 7：部署觀測與規範回填 ⬜

- **動作**：
  1. 部署後在 Firebase Console（Usage）對照「每日讀取曲線」與
     統計頁的用量資訊，確認三張清單重複進出不再產生讀數。
  2. 重現原爆點場景（下午管理操作 4～5 次）量測實際讀數。
  3. 依結果回填 `docs/資料庫讀取規範.md`（三節表格、TTL 基準、
     「刻意保留」清單若有增減）。
- **驗收**：讀取量明顯下降、無 stale／權限異常回報；規範與實作一致。

## 三、明確不做（與理由）

| 目標 | 不做理由 |
|---|---|
| `api/admin/stats`、`roles`、`feature-modules`、`downloads` | 業務資料已 0 讀或已走既有快取，剩的只有驗證基線 2 讀（歸 Phase 5 管） |
| 榜單「我的紀錄」（每人 1 讀精準查） | 收益 1 讀，但送出成績後要立刻看到新分數，快取風險不划算 |
| `keepalive` | 已是 0 讀（`verifySessionForRenewal`），最優解 |
| 單筆孤兒銜接（`roster/link` 走 `moveEntriesUid`，約 9～14 讀） | 一次性 mutation、正確性要求即時，不可快取；若日後要壓，方向是改 `in` 分塊合併查詢（查詢重構，不是快取） |
| 榜單 TOP 前 100 | 已有 15 秒 `cachedRead`＋寫入後失效 |
| `onSnapshot`／輪詢 | 規範第五節：不存在即不存在，**不要新增**常駐即時監聽 |
