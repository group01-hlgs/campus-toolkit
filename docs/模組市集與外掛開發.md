## 一、定位與範圍

### 1.1 三方角色與系統邊界

```
 開發者（任何人）            模組市集（獨立系統）            學校（fork 的主程式）
 ──────────────            ─────────────────              ────────────────────
 外部 repo＋模組模板   →    投稿 zip（審核制）        →    /admin/modules/market 瀏覽
 module:check 自驗          上架：版本＋sha256              超管點「安裝」
                            公開目錄 API                    → 程式碼進 fork → 自動部署
                                                           超管開總開關（啟用）
                                                           各身分使用
```

- **開發者**：不需主程式 repo 權限，在自己的 repo 依公開契約開發。
- **模組市集**：獨立 repo、獨立部署（比照 `主題市集規劃書.md` §1.1 定位），只管目錄、審核、版本與套件儲存；**不含任何學校資料**。
- **學校**：主程式以 GitHub fork ＋ Vercel 部署（沿用原文件 §2.3 前提）；安裝的原子單位仍是**「合併＋部署」**（原文件 §5 決策不變）。

### 1.3 前提

1. 學校主程式部署於 GitHub（fork）＋ Vercel，push 自動 build——即原文件 §2.3 的既有定案。
2. 主程式側 **P1–P3 先落地**（manifest 自動註冊、薄轉接檔、`module:install` 腳本）——本文件全部架在其上（原文件 §8 分期，不重複展開）。
3. 市集只服務 `kind: "optional"` 的模組；主程式模組（builtin）不入市集（原文件 §1）。

### 1.4 不做的事（本文件範圍外）

- **不做「不重部署即安裝」**（原文件 §2.3 已否決）：無微前端、無運行時載入、無放寬 CSP。
- 市集不存學校資料、不負責啟用狀態；啟用一律在學校主程式內操作。
- 第一期不做模組評分／留言／收藏（避免審核成本擴大，同主題市集決策）。
- 第一期不做多市集來源（見開放問題 #1）。

## 二、架構總覽與關鍵決策

### 2.1 全生命週期

```
【開發】外部 repo（模板）
   ├─ module.json（contractVersion、minHostVersion…）【E1】
   ├─ 本機 link 進主程式副本實測【E2】
   └─ npm run module:check（SDK 靜態掃描）【E4】【E5】
        │ 投稿（zip ＝模組資料夾本身）
        ▼
【發布】模組市集
   ├─ schema 驗證＋靜態掃描＋人審（審核制）
   ├─ 上架條件：status=live、href 非空、check 全過
   └─ 儲存：版本＋sha256（下架即失效）
        │ 目錄 API（公開）
        ▼
【安裝】學校超管 /admin/modules/market 點「安裝」【E3】
   ├─ 伺服端 fetch（MODULE_MARKET_URL 常數，不信使用者輸入網址）
   ├─ 驗證鏈：schema → sha256 → contractVersion → minHostVersion → hooks【E9】
   ├─ 依賴檢查：無新依賴【E10】
   ├─ GitHub API：commit src/modules/<value>/** ＋ module.lock.json
   └─ push → Vercel build（P1 掃描 manifest → 自動產生註冊表＋轉接檔）
        │ 上線，但 featureModulesEnabled 查無此鍵 ＝ 未啟用（fail-safe）
        ▼
【啟用】/admin/modules 開總開關＋選身分顯示（＝原文件 §5，完全沿用）
        ▼
【使用】首頁卡片、權限閘門、掛勾（公告／行事曆）——＝原文件 §2.2 管線
        ▼
【更新】市集出新版 → 管理頁顯示「有新版本」→ 同安裝管線換版【E7】
【卸載】反向 commit（移除資料夾＋lock）；資料預設保留【E6】
```

### 2.2 關鍵決策

| # | 決策 | 說明 |
|---|---|---|
| D1 | 安裝＝**程式碼進 fork（vendored）**＋lock 鎖定 | 不採「build 時從市集下載」——市集當機不可拖垮學校建置；程式碼在 repo 內，diff 可審、離線可 build |
| D2 | 安裝由**主程式 server 以 GitHub API 提交** | 學校只需在 Vercel 設 2 個環境變數（§5.1）；無 token 走手動安裝備援（§5.7） |
| D3 | **單一官方市集** | `MODULE_MARKET_URL` 寫死常數（env 覆寫僅供測試），比照主題市集決策 #9 |
| D4 | **審核制**＋雙邊同一組驗證案例 | 投稿端與安裝端跑同一 manifest 驗證（同主題市集附錄 A 模式） |
| D5 | 契約版本化 | `contractVersion`（契約 schema 版）與 `minHostVersion`（主程式版本 `0.379` 格式）分離；不相容即拒絕安裝 |
| D6 | 模組包＝**純原始碼、零新依賴** | 只含模組資料夾；`package.json` 若存在僅供展示，`dependencies` 一律不生效【E10】 |
| D7 | 展示資料與契約分離 | 截圖、審核狀態、下載數存市集側；`module.json` 只描述程式碼契約 |
| D8 | 安裝≠啟用 | 完全沿用原文件 §1/§5；安裝後 fail-safe 為關，超管再手動啟用 |

### 2.3 開發角色與環境三層【E11】（對話補強）

> 本節源自「工程師要在什麼環境建置外掛」的討論；原文件 §4 僅述「主 repo 開分支」，未展開角色、fork 工作流與測試資料隔離。

**角色——乙做插座、甲做插頭，順序永遠是「乙的機制 → 甲的模組」：**

| 角色 | 職責 | 動作 |
|---|---|---|
| **乙**（主程式擁有者） | 建外掛機制＝協議（`module.json`）＋掛載點（`src/modules/`）＋自動註冊（掃描器） | **先行**（＝原文件 P1；落地順序見 §7） |
| **甲**（模組開發者） | 照協議開發插頭 | 無 A 權限 → GitHub fork A → clone → 分支；有權限 → 直接 clone → 分支 |

**開發環境三層**（缺一不可；模組不是獨立應用，沒有宿主開不起來）：

```
① 模組資料夾 src/modules/<value>/（原始碼、manifest、自己的 git 生命週期）
     │ 掛進方式：主 repo 開分支；或 `module:link` 外部 repo（P3 已落地 0.386，watch 驗收【E14】屬期 2）
     ▼
② 主程式宿主（clone／fork）——唯一能「跑起來」的地方
   ├─ npm install（主程式既有依賴＝模組唯一可用依賴【E10】）
   ├─ .env.local（FIREBASE_SERVICE_ACCOUNT_KEY、SESSION_SECRET 等，照 .env.example）
   └─ npm run dev → localhost 測試
     ▼
③ Firebase 專案（與宿主同一個；模組不另開專案，server-only 金鑰）
```

- **fork/clone 判定**：`clone`＝拉到本機（**測試全在這裡**，與線上無關）；`fork`＝GitHub 上換寫入權限（僅無 A 權限者需要）。只有 `git push main` 觸發部署——「不能在 A 上測試」是誤解，不能的是「push A 的 main」。
- **測試資料隔離**：本機 dev 連的是**真 Firestore 專案**（`.env.local` 金鑰），測試寫入會污染正式資料。三選一：① 統一前綴（`dev_`）＋測完清理；② 另開 Firebase 專案、`.env.local` 指過去（最乾淨）；③ Firestore Emulator（`firebase.json` 需加設定）。
- **同步與相容性管理**：只碰自己資料夾 → 同步 A **零 git 衝突**；但**「不衝突 ≠ 不會壞」**——A 若改了模組依賴的介面（`requireAdminModule`、`AdminSectionShell` props、Next 大版升級），模組會編譯/執行失敗，屬**相容性問題**。管理手段：常同步（分叉越久問題越大）＋同步後必跑 §3.4 驗證迴圈；市集層以 `contractVersion`／`minHostVersion`【E1】正式化。

## 三、外掛開發規格（開發者側）

### 3.1 模組 repo 與模板【E2】

模組**自己的 repo**，內容即原文件 §3.1 目錄約定的模組資料夾本身：

```
<module-repo>/                     ← 對應安裝後的 src/modules/<value>/
├── module.json        # manifest（§3.3 範例）
├── README.md          # 說明、開發者、版本、安裝後設定方式
├── admin/  api/  components/  lib/  types/
├── tests/
│   └── contract/      # 契約測試案例（依附錄 A）
└── package.json       # 僅 scripts（module:check），dependencies 不生效【D6】
```

**開發期不孤獨**：主程式副本（本地 clone 或 fork）執行 `npm run module:link -- <本 repo 路徑>`，以目錄連結掛進 `src/modules/<value>`，即可 `npm run dev` 完整實測（P3「複製/連結」的反向運用）。開發完成後**連結移除**，發布物＝資料夾內容本身。

主程式核心檔在開發期間**凍結**（原文件 §4 第 1 條）；需公開面新增時，另開 PR 說明——這是外部開發者的正規回饋管道。

**型別解析與檢查環境【E14】**：模組程式碼 import `@/lib/dal` 等路徑別名，離開宿主 `tsconfig` 即編不過——外部 repo **不能獨立 `tsc`**。定案：

1. `module:check`（靜態掃描）由 SDK 提供、可獨立執行；**需要 tsc 的檢查一律在宿主環境跑**（link 掛入後 `npm run lint`，或市集端影子 tsc，見 §3.2）。
2. SDK 內附 `tsconfig.base.json` 樣板（`paths` 指向宿主 stub／型別快照），讓外部 repo 的編輯器與 CI 能做**基本**型別提示（完整驗證仍以宿主為準）。

**`module:link` 實作風險【E14】**：本專案開發機為 win32＋Next 16（dev 預設 Turbopack），**外部目錄 symlink 是否被 dev watch 掃得到屬未驗證風險**——列為 §7 期 2 的驗收項（於宿主 `npm run dev` 改動模組檔案→瀏覽器即時更新才算過）；備案＝`module:link` 改為 **copy-sync**（檔案監聽雙向同步），契約不變。

### 3.2 SDK 與契約版本【E4】

新 repo：**`module-sdk`**（npm 或 git 套件），內容：

| 內容 | 說明 |
|---|---|
| `MODULE_CONTRACT_VERSION` | 契約版本常數（目前 `1`）；與 manifest `contractVersion` 比對 |
| 型別快照 | 原文件 §3.3 允許面的 `.d.ts`：`@/lib/dal`、`@/lib/audit`、`@/lib/announcements`（`publishFromModule`）、`@/lib/calendar`（`publishScheduleFromModule`，0.379 已實作）、`AdminSectionShell` props 等 |
| manifest JSON Schema | `module.json` 結構驗證（雙邊同一份） |
| `module:check` CLI | §6.3 靜態掃描規則的實作（投稿端與安裝端共用） |
| **影子 tsc**【E14】 | 以型別快照＋`paths` 別名 stub 對模組原始碼跑 `tsc --noEmit`——讓**市集端**能攔下型別錯誤（原缺口：靜態掃描保證不了型別，安裝後才在 Vercel build 爆）。宿主端 lint 仍是最終判定 |
| 可依賴白名單 | §3.3 表格的機器可讀版＋主程式既有 npm 依賴清單（React、Next、xlsx…）【E10】 |

**穩定性承諾**：同一 `contractVersion` 內，§3.3 允許面只增不改不刪；破壞性變更才遞增版本，舊版模組保留相容判斷（同主題市集 `schema_version` 態度）。

```jsonc
    { "kind": "api",  "path": "/api/admin/exam-registration" }

  "permission": { "mode": "new", "value": "examRegistration", "category": "校務資料" },
  "icon": "examRegistration",
  "rateLimits": [
    { "key": "EXAM_REGISTRATION_GET",   "limit": 60, "windowMs": 60000 },
    { "key": "EXAM_REGISTRATION_MUTATE", "limit": 20, "windowMs": 60000 }
  ],
  "auditActions": ["exam_registration_updated", "exam_registration_closed"],
  "dataCollections": ["examSessions", "examSignups"],   // 【E1】升級為安裝驗證項

```

規則（前 4 條沿用原文件 §3.2，後 4 條為擴充）：

1. `value` 全域唯一；與註冊表重複 build 期報錯（原樣）。
2. manifest 是唯一註冊來源（原樣）。
3. `status` 由作者宣告，僅為展示資訊；可否啟用由超級管理員總開關決定【0.387 起與原樣不同】。
4. `rateLimits.key`、`auditActions` 帶模組代碼前綴（原樣）。
5. **【E1】** `contractVersion` ＞ 主程式當前契約 → 拒絕安裝（訊息：請升級主程式）。
6. **【E1】** `minHostVersion` ＞ 學校主程式 `src/version.json` → 拒絕安裝。
7. **【E1】** `dataCollections` 為**宣告即承諾**：掃描保證模組程式碼只讀寫所列集合＋允許的掛勾集合（`announcements`、`calendarEvents` 自動豁免）。
8. **【E8】** 市集展示資料（截圖、審核狀態、下載數）**不入** manifest。
9. **【E14】** `firestoreIndexes` 選填：宣告模組查詢所需複合索引（欄位順序即建索引順序）。安裝成功後於回應列出**待建索引提示**；漏宣告而踩 `FAILED_PRECONDITION` 屬作者職責（同主程式 0.375 實例——範圍查詢＋`array-contains` 需複合索引）。

### 3.4 開發與本地驗證流程

1. 取模板 repo → 改 `value`（全域唯一，先查市集目錄 API 查重）。
2. `module:link` 掛進本地主程式 → 實作 → 四身分手測（可見性、權限不足路徑）。
3. `npm run module:check`：manifest schema、白名單 import、前綴、依賴、集合宣告、六鐵律清單核對（§6.3）。
4. 對照原文件 §7 相容性檢查清單逐項核對。
5. 本機 `npm run lint`（在主程式端跑，確保 tsc 通過）。
6. **同步主程式**（fork 工作流）【E11】：`git fetch upstream && git merge upstream/main`（upstream＝乙的 A）。只碰自己資料夾＝零 git 衝突；但同步後**必回步驟 3–5 重跑**——A 可能動了你依賴的介面（相容性問題，見 §2.3）。
7. **掛入驗證迴圈**【E12】：每次改動與同步後跑 5 項——① `npm run lint` → ② `/admin/modules` 出現本模組卡 → ③ 模組頁可開（無權限被擋）→ ④ API 正常、無權限回 403 → ⑤ 首頁卡片依設定顯示。**5 項全過才算「掛得上、沒壞」**（驗收版見 §8）。

### 3.5 模組包（package）規格【D6】【E10】

| 項目 | 規定 |
|---|---|
| 內容 | 只有模組資料夾本身的檔案；不含 `node_modules`、不含主程式路徑 |
| 體積 | 壓縮後 **≤ 500KB**（投稿端與安裝端都檢查） |
| 依賴 | **禁止引入主程式沒有的 npm 依賴**——安裝只複製資料夾，主程式 `npm install` 不會裝模組依賴；`package.json.dependencies` 存在即拒絕（v2 試開放宣告式安裝，見開放問題 #5）。**【E15】v1 亦禁依賴其他模組**（掃描禁止 import `src/modules/<其他 value>`；掛勾是唯一合法的跨模組輸出管道） |
| 編碼 | UTF-8 繁體中文；README 必填（含安裝後設定說明、資料集合清單、掛勾需求） |
| 驗證 | `module:check` 通過證明（附報告欄位，市集複驗） |

### 3.6 發布（投稿）

市集 `/submit`（會員制，比照主題市集 §8）：

```
開發者上傳 zip（module:check 報告隨包）
  → 市集：schema 驗證 → sha256 → 靜態掃描複驗 → status=審核中
  → 管理員人審（程式碼檢視、README、資料集合合理性）
  → 上架（寫入 versions 子文件，downloads 歸零）
  → 更新版：作者 PATCH 新版本 → 回「審核中」重審（同主題市集 §8.3）
```

## 四、模組市集（獨立系統）【E8】

### 4.1 定位

比照 `主題市集規劃書.md` §1.1：**完全獨立 repo**，不引用主程式程式碼（manifest schema 複本雙邊同步）；公開瀏覽**免登入**（目錄、詳情、README），投稿與管理需登入；**審核制**。技術棧同主題市集：Next.js App Router ＋ Firestore。

**schema 單一來源【E15】**：「雙邊同步」不得靠人工抄——manifest JSON Schema 與附錄 A 案例**只存在於 `module-sdk`**，市集以 git 依賴釘到明確 tag（`github:<owner>/module-sdk#v1.x`）引入；SDK 出破壞性版才升 tag，雙邊版本差異在 CI 比對即報錯。

### 4.2 資料層（Firestore）

**`modules` collection**（文件 ID ＝ `value`，全域唯一）

| 欄位 | 型態 | 說明 |
|---|---|---|
| `value` / `label` / `description` | string | 摘要（列表用，不含 package） |
| `kind` | string | 恆 `"optional"`（市集只收功能模組） |
| `author` / `authorUrl` / `ownerId` | string | 作者與投稿者 uid |
| `keywords` | string[] | ≤ 8 個，每項 ≤ 12 |
| `status` | string | `審核中` / `已上架` / `已下架` / `被拒絕` |
| `latestVersion` | string | 當前上架版本 |
| `downloads` | number | `FieldValue.increment(1)`（best-effort） |
| `reviewNote` | string? | 拒絕原因／審核備註 |
| `screenshots` | string[]? | 截圖路徑（≤ 5 張，展示用） |
| `createdAt` / `updatedAt` / `publishedAt` | timestamp | 同主題市集語意 |

**`moduleVersions` subcollection**（doc id ＝ 版本號）

| 欄位 | 說明 |
|---|---|
| `version` / `contractVersion` / `minHostVersion` | 版本與相容資訊 |
| `sha256` | 套件雜湊（安裝端鎖定） |
| `size` | 壓縮後位元組（≤ 500KB 驗證） |
| `manifest` | 解析後的 `module.json`（詳情頁展示、目錄 API 回傳） |
| `packageBase64` | 套件本體（≤ 500KB，Firestore 文件上限內；超過改儲存方案見開放問題 #4） |
| `changelog` / `createdAt` | 更新說明與時間 |

**`moduleSubmissions`**（稽核）：`value`、`ownerId`、`action`（投稿／更新／上架／下架／拒絕）、`note`、`createdAt`。
**`members` / `admins` / `settings/market`**：比照主題市集 §3.3、§3.4（初期不開放自助註冊）。

**查詢策略**：比照主題市集 §4.1 第一期——`GET /api/modules` 回不含 `packageBase64` 的摘要陣列，全部 `status == "已上架"` 以 `cachedListRead` 快取，前端搜尋／標籤／分頁；詳情單點 `.doc(id).get()`。

### 4.3 公開 API

| 端點 | 方法 | 認證 | 回傳 |
|---|---|---|---|
| `/api/modules` | GET | 公開 | `{ ok, total, page, modules: [摘要] }` |
| `/api/modules/{value}` | GET | 公開 | `{ ok, module, versions: [版本摘要（無 package）] }` |
| `/api/modules/{value}/versions/{v}` | GET | 公開 | 詳情（manifest、sha256、size、changelog） |
| `/api/modules/{value}/versions/{v}/download` | POST | 公開 | `{ ok, packageBase64, sha256 }`（計數、限流） |
| `/api/modules` | POST | 會員 | 投稿（`status=審核中`） |
| `/api/modules/{value}` | PATCH | 作者／管理員 | 更新 meta／新版本（回審核中） |
| `/api/admin/modules` | GET | 管理員 | 四狀態列表 |
| `/api/admin/modules/{value}/review` | POST | 管理員 | `publish` / `unpublish` / `reject` |

錯誤格式、限流、稽核：同主題市集 §5.1、§8.2（投稿 24h 上限、失敗鎖定）。

### 4.4 與主程式的對接

同主題市集 §5.2 模式，主程式側新增（本文件 §5.2 展開）：

- `MODULE_MARKET_URL` 常數（env 覆寫僅測試）；**只 fetch 常數網址**，不信任何使用者提供網址。
- 雙邊驗證同一份 manifest schema 與附錄 A 案例；`schema`／契約版本各自保留相容判斷。

### 4.5 安全（市集側）

| 項目 | 措施 |
|---|---|
| 套件完整性 | sha256 雙邊鎖定；下架＝刪除 `packageBase64`，下載即 404 |
| 體積 | ≤ 500KB（投稿與下載雙檢） |
| 靜態掃描 | `module:check` 同款規則複驗（§6.3），失敗不可上架 |
| 人審 | 所有投稿與新版本經管理員檢視程式碼後上架 |
| 權限 | 審核／上下架伺服端 `role == "admin"`，不信任前端 |
| 稽核 | `moduleSubmissions` 全記錄 |
| CSRF／限流 | 一次性 nonce；下載端點限流 |

## 五、主程式側整合：安裝／更新／卸載【E3】

### 5.1 環境變數與前提（學校 fork 側）

| 變數 | 說明 |
|---|---|
| `MODULE_MARKET_URL` | 官方市集網址（缺省用程式常數） |
| `MODULE_GIT_TOKEN` | PAT（`contents: write`），供 server 提交進本 fork |
| `MODULE_GIT_REPO` | `owner/repo`（本 fork）；`MODULE_GIT_BRANCH` 預設 `main` |

**未配置 token ＝ 安裝頁改顯示「手動安裝」指引（§5.7），不報錯**（fail-safe 朝關）。

### 5.2 市集瀏覽與取回端點

- 頁面：`/admin/modules/market`（超級管理員，比照 `/admin/modules` 併入同一管理區）——目錄、搜尋、詳情、README、已安裝／可更新標記、安裝／更新／卸載按鈕。
- 端點：`GET /api/market/modules/{value}`（superadmin 守門）→ server fetch `MODULE_MARKET_URL` → 狀態碼、體積、`JSON.parse` → manifest schema 驗證 → 回 `{ ok, module, pkg }`。失敗回 400 中文訊息。

### 5.3 安裝管線（驗證鏈＋GitHub 提交）

```
超管點「安裝」（POST /api/admin/market/install { value, version? }）
  1. isSuperAdmin 守門＋assertSameOrigin＋RATE 桶（MARKET_INSTALL）＋稽核準備【E13】
     （安裝前確認對話框：manifest 摘要、檔案清單、sha256，輸入 value 確認）
  2. server fetch 套件（§5.2）
  3. 驗證鏈（任一失敗即中止，逐項回中文訊息）：
     ① sha256 對得上市集宣告
     ② module.json schema 合法；kind=optional、status=live、href 非空
     ③ value 全域唯一（未安裝、未與 builtin／既有模組撞名）
     ④ contractVersion ≤ 主程式 MODULE_CONTRACT_VERSION【E1】
     ⑤ minHostVersion ≤ src/version.json【E1】
     ⑥ module:check 掃描（白名單 import、前綴、無新依賴、集合宣告）【E5】【E10】
     ⑦ hooks 宣告的掛勾主程式已實作（宣告了尚未實作的掛勾 → 警示但不阻擋；`announcements`、`calendar` 現皆可用）【E9】
     ⑧ 體積 ≤ 500KB
     ⑨ routes 前綴白名單＝`/admin`／`/student`／`/parent`／`/staff`（其前綴之外的頁面
        無 `src/proxy.ts` 角色閘門 → 拒絕）；且 routes 路徑不得與 src/app/** 既有
        路由撞名（撞名＝build 失敗）【E13】
     ⑩ lock ↔ 目錄一致性：module.lock.json 與 src/modules/*/module.json 分家
        （手動 revert／手動放資料夾／merge 衝突）→ 中止並提示先修復【E13】
  4. Git Data API 一筆 commit：
     - 新增/覆寫 src/modules/<value>/**（更新時先刪舊樹）
     - 更新 module.lock.json（§5.4）
     - 連同 node scripts/version.js（版本 bump 紀律，見下）【E13】
  5. push → Vercel 自動 build（P1/P2 build 期產生註冊表＋轉接檔）
  6. 回應：{ ok }＋「已提交部署，尚未啟用 → 前往功能模組頁啟用」
     （部署狀態見管理頁安裝紀錄，見下方「部署回饋」）
```

- **端點守門【E13】**：除 `isSuperAdmin` 外必須 `assertSameOrigin`（本專案變更端點慣例）——此端點等同「可寫 repo」，屬最高風險操作，前端另加確認對話框。
- **部署回饋【E13】**：「build 失敗＝revert」必須有**偵測者**——app server 看不到 Vercel build 結果，原文件與本文件 v1.1 皆未定義，補規格：① 安裝回應先回「已提交，部署中」；② 管理頁安裝紀錄輪詢 GitHub commit status／Vercel deployment 狀態（30 秒一次、上限 10 分鐘）；③ 失敗顯示「部署失敗」＋**一鍵 revert**（反向 commit，含 lock）；④ 超管未確認成功前，管理頁顯示警示橫幅。**v2 備選**：改走 branch＋PR＋Vercel Preview，綠燈才 merge——順帶讓超管安裝前看得到 diff（見開放問題 #10）。
- **版本 bump 紀律【E13】**：安裝／更新／卸載的自動 commit 須連同執行 `node scripts/version.js`、commit 訊息以「版本號更新至 0.xxx」結尾（與 `AGENTS.md` 交付慣例一致）——否則 `src/version.json` 不動、各部署環境版本顯示不一致，`minHostVersion` 比對基準的語意也含糊。
- **失敗原子性**：驗證鏈（含 ⑨⑩）在提交前完成；部署失敗走上方一鍵 revert（原文件 §5「失敗就 revert」）。
- **並發**：Git ref 更新衝突 → 重試一次，仍衝突回「請稍後再試」。

### 5.4 `module.lock.json`（安裝清單，存於 fork repo 根目錄）

```jsonc
{
  "lockVersion": 1,
  "modules": [
    {
      "value": "examRegistration",
      "version": "1.2.0",
      "contractVersion": 1,
      "minHostVersion": "0.379",
      "sha256": "…",
      "source": "market:<MODULE_MARKET_URL>",
      "installedAt": "2026-10-09"
    }
  ]
}
```

用途：已安裝清單的**單一真相**（管理頁比對更新、掃描器排除重複註冊）、完整性稽核、卸載定位。**掃描器與轉接檔產生器一律 build 期執行、不入 commit**（保持生成物零手改，原文件 P1/P2 規格）。

**一致性檢查【E13】**：build 期掃描器須比對 lock ↔ `src/modules/*/module.json`——lock 有而資料夾無＝殘 lock；資料夾有而 lock 無＝手放未登記。**不一致即 build 失敗（fail-fast）**，訊息指向手動安裝/卸載流程修復。兩份真相分家常見於手動 `git revert`、手動放資料夾與 lock 的 merge 衝突（安裝端⑩只擋主動安裝，擋不了改 repo 的人）。

### 5.5 更新與回滾【E7】

- **更新**：管理頁顯示「有新版本」（目錄 `latestVersion` vs lock）→ 走同一安裝管線（覆寫資料夾＋lock 版本遞增）→ build 部署。**更新前先驗證新版本契約**（§5.3 ④⑤），不相容 → 拒絕並建議先升級主程式。
- **主程式升級的相容閘門【E15】**：`minHostVersion` 只在安裝時查一次——學校日後升級主程式時，build 期掃描須比對各已安裝模組 lock 的 `contractVersion` 與當前 `MODULE_CONTRACT_VERSION`，**不相容者列警示清單**（管理頁紅字標示，不阻擋部署：舊契約模組多半仍可跑，破壞性變更才需作者出新版）。
- **回滾**：① 市集仍存舊版 → 「安裝指定舊版」；② 緊急 → fork `git revert` 該安裝/更新 commit → push（最短路徑，無需市集）。
- 模組資料（Firestore）**不隨版本變動搬移**——schema 遷移是模組作者職責，寫進 README。

### 5.6 卸載與資料處置【E6】

1. 前置檢查：啟用狀態先由超管關閉（或卸載流程自動關閉 `featureModulesEnabled` 該鍵）。
2. commit：刪 `src/modules/<value>/**`＋lock 該列 → build 部署 → 入口與卡片消失（fail-safe）。
3. **資料預設保留**：`dataCollections` 所列集合不動（留待日後匯出／清查）。
4. **選擇性清除**（另一次獨立操作）：二次確認（輸入 `value`）→ 依宣告集合逐一清除 → 稽核 `module_data_purged`。掛勾寫入的公告／行程**不在**清除範圍（屬主程式設施）。
5. 權限單位：`permission.mode: "new"` 的可指派單位隨模組消失，名冊上的殘指派由既有清理邏輯處理（實作時於 P1 權限合併一併定案）。
6. **【E15】市集下架不撤銷**：vendored 程式碼不因市集下架而失效（D1 的既有含義，明文化）——資安問題走「市集公告 → 學校手動更新/卸載」；主程式僅在安裝/更新時連線市集，運行期零依賴。

### 5.7 手動安裝（無 token 備援）

1. 市集詳情頁「下載套件」（或作者直接提供 zip）。
2. 學校在本機 fork 執行 `npm run module:install ./<value>-<version>.zip`（＝原文件 P3 腳本，來源從目錄改為本地檔）——同一條驗證鏈（含 §5.3 ⑨⑩）。
3. `git push` → 自動部署（腳本連同執行 `version.js`，版本 bump 紀律同 §5.3）。

### 5.8 安裝後（完全沿用原文件，不重複）

啟用＝`/admin/modules` 開總開關＋選身分顯示；runtime 生效、稽核 `feature_module_updated`、首頁卡片即時出現——見原文件 §5 與 §2.2 管線。

**模組設定與資料初始化（契約，【E14】）**：`settings/*` 被禁（原文件 §3.3 禁 5）→ 模組設定存**自己的集合**（須列入 `dataCollections`，慣例 `<value>Settings` 單文件）；初始化採 **lazy init**（API 首次讀取缺檔即建預設值）——安裝管線只管程式碼，**不提供 post-install hook**，資料層由模組自己負責並寫進 README。

## 六、信任與安全【E5】

### 6.1 風險聲明

第三方模組是**跑在学校伺服器上的原始碼**：API 路由具備 `firebase-admin` 權限（firestore.rules 對客戶端全拒，伺服器端即全權）。本規劃的信任模型＝**「審核過的代價透明」**，分層防線如下；不 pretending 這與內建模組同等安全——學校超管以「安裝」此一動作承擔信任（安裝全程稽核、可隨時卸載回滾）。

**客戶端外來碼風險【E15】**：模組頁面是 `"use client"`，程式碼會進**第一方 bundle 跑在學校管理者的瀏覽器**——風險不在資料庫，而在：讀 DOM／攔截 fetch／外傳畫面上的資料（same-origin、CSP 不設防）。防線：① 模組頁面**僅限管理端**起步（開放問題 #7）；② §6.3-8 掃描禁碰 `document.cookie`／`localStorage`／`sessionStorage`（session 為 httpOnly cookie，掃描意在擋無故持久化憑證）；③ 第一方 bundle 本就來自同一 repo——此風險與「直接 merge 陌生 PR」同級，仍由審核承擔，不 pretending 可被掃描根除。

### 6.2 六道防線

| # | 防線 | 時機 |
|---|---|---|
| 1 | **審核制**：人審程式碼＋README＋資料集合合理性 | 市集上架 |
| 2 | **靜態掃描** `module:check` 雙邊複驗（§6.3） | 投稿＋安裝 |
| 3 | **契約面最小化**：只准依 §3.3 公開面；白名單 import | 掃描強制 |
| 4 | **集合宣告** `dataCollections`：只准讀寫所列集合＋掛勾集合 | 掃描（v1）→ runtime（v2） |
| 5 | **完整性**：sha256 鎖定＋審核上架才可下載 | 安裝 |
| 6 | **可逆**：lock 追蹤、一鍵卸載、git revert 回滾、全程稽核 | 事後 |

### 6.3 靜態掃描規則（`module:check`，市集與安裝共用）

1. import／require **白名單**＝原文件 §3.3 允許表；核心檔（兩張註冊表寫入面、`ModuleIcon`、`rate-limit` `RATE`、`audit` 聯集、`RoleHome`）一律禁止 import（生成物除外）。
2. 禁直接讀寫 `settings/system`（原文件 §3.3 禁止 5）。
3. 禁自建平行公告／行程集合；`publishFromModule`／`publishScheduleFromModule` 之外禁寫 `announcements`／`calendarEvents`（原文件 §6 總則 1）。
4. `rateLimits.key`、`auditActions` 前綴＝`value`（轉_snake/camel 由模板定案）。
5. 禁新增依賴：`package.json.dependencies` 非空即拒絕；import 不在主程式依賴白名單即拒絕【E10】。
6. `dataCollections` 之外的 Firestore 集合字面值比對（字串掃描，誤報可於 manifest `dataCollections` 補宣告排除）。
7. 六鐵律中可自動化者（如 `get()` 迴圈內連續 query 的 N+1 樣式）盡量檢查；其餘維持 §3.4 步驟 3–5 的人工清單核對。
8. **【E15】** 客戶端元件（`"use client"` 檔）禁讀寫 `document.cookie`、`localStorage`、`sessionStorage`，禁 `eval`／`new Function`——防無故持久化憑證與動態執行（見 §6.1 客戶端風險）。
9. **【E15】** 禁 import 其他模組資料夾（`src/modules/<非自己 value>/**`）——v1 禁模組相依（§3.5）。
10. **【E15】** `routes[].path` 必須落在 `/admin`／`/student`／`/parent`／`/staff` 四前綴且與既有路由不撞名（與安裝鏈⑨同規則，雙邊共用案例：附錄 A #14、#15）。

### 6.4 Runtime 集合存取管制（v2，候選）

`@/lib/firebase-admin` 提供 `scopedDb(moduleValue)`：依已安裝模組的 `dataCollections` 宣告，於檔案／查詢層攔阻未宣告集合（經 `module.lock.json` 取得宣告）。屬原文件 3.3「僅伺服器端 `getAdminDb()`」的**收斂**而非開放，列 v2（開放問題 #6）。
