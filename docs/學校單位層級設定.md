# 學校單位層級設定（單位層級設定）

「學校基本設定」`schoolSettings`（僅超級管理員）底下的第一個子功能，
暫定子功能代碼 `schoolSettings.org`（正式歸屬待 `功能模組與權限架構.md` 定稿）。
管理人員自行決定學校層級數與每層名稱，並設定每個單位（處室、組別）的層級與上級單位。

- **入口**：管理員首頁 →「學校基本設定」卡片 → 子功能入口卡片「單位層級設定」
  → `/admin/school-settings/org`。
  「學校基本設定」頁（`/admin/school-settings`）本身是**子功能入口卡片牆**，
  版頭、權限閘門與頁尾由共用 `school-settings/layout.tsx` 提供，新增子功能＝加一張卡片＋一個子路由。
- **結構性資料、不按學期**：學期轉換不會影響，與 `roleEnabled` 同屬現行狀態。
- **不在權限樹內**：本功能只建立組織結構資料；權限表單的處室分組仍用靜態常數，
  兩者以單位 `code` 於日後再串接（見「與其他功能的關係」）。

## 名詞

| 名詞 | 說明 |
|---|---|
| 學校層級數 | 本校組織有幾層（1～5），例如「處 → 組」＝2 層 |
| 層級名稱 | 每一層的稱呼，如「處室層級」「組別層級」；未自訂時為「第一層」… |
| 單位 | 一個處室、組、中心等節點 |
| 上級單位 | 該單位的直接上層；最上層單位沒有上級 |

## 資料模型

存於 **`settings/school`**（與 `settings/system` 同集合的獨立文件）。
刻意不放 `settings/system`：系統設定的 PUT 是整份覆寫、只保留 `roleEnabled`
（`src/app/api/settings/route.ts`），混放會在下次儲存系統設定時被清掉。

```ts
interface OrgUnit {
  code: string;           // 穩定代碼：新增時產生、改名不變（供日後引用）
  name: string;           // 單位名稱（同上級內唯一，≤ 40 字）
  level: number;          // 1..levelCount
  parent: string | null;  // 上級單位 code；最上層必為 null
}
interface OrgStructure {
  levelCount: number;       // 1..5
  levelLabels: string[];    // 長度恆等於 levelCount（≤ 20 字）
  units: OrgUnit[];         // 扁平陣列，兄弟順序＝陣列相對順序，上限 200 筆
}
```

- 常數與型別：`src/types/org.ts`（**不含 `server-only`**，前端與 API 共用驗證）。
- 空庫＝`{ levelCount: 2, levelLabels: ["第一層", "第二層"], units: [] }`。

## API

`src/app/api/admin/school/org/route.ts`

| 方法 | 行為 |
|---|---|
| `GET` | 讀回設定；`readOrgStructure()` 寬容修正型別與範圍，毀損不整份作廢 |
| `PUT` | body `{ org }`，整份覆寫 `settings/school`；驗證不過回 400 且不寫入 |

- 守門：`requireAdminModule("schoolSettings")` —— `adminModulesOf` 對非超級一律剝除
  該模組，因此等同「僅超級管理員」，與頁面層判斷同一把尺。
- 其他：`assertSameOrigin`、限流 `SCHOOL_ORG_GET`（60/分）／`SCHOOL_ORG_MUTATE`（20/分）、
  稽核 `logActivity("school_org_updated")`（details 記層數與單位數）、`Cache-Control: no-store`。

## 伺服器驗證規則

`validateOrgStructure()`（API 與表單共用，任一不過即 400）：

1. `levelCount` 為 1～5 的整數；`levelLabels` 長度＝層級數、每項非空 ≤ 20 字。
2. `units ≤ 200`；`code` 非空且全域唯一；`name` 非空 ≤ 40 字，**同一上級單位內唯一**。
3. `level` 在 1..levelCount 之內。
4. `level === 1 ⇔ parent === null`。
5. `parent` 必須存在，且 `parent.level === unit.level - 1`
   （**此條同時封死環狀引用**：要成環需無限往下）。
6. 無子單位才可刪除（前端先擋，伺服器同規則）。

## 搬移規則（表格與拖曳共用）

改上級或層級時，**整棵子樹一起平移**（`setUnitParent`／`setUnitLevel`）：

- 新層級由上級推導：`parent ? parent.level + 1 : 1`。
- 上級不可是自己或自己的後代。
- 平移後最深層 > `levelCount` → 拒絕，訊息「其下尚有子單位，搬移後會超出學校層級數」。
- 新單位插到新上級的**子層末尾**（兄弟順序＝陣列相對順序）。
- 同層順位可用表格的「上移／下移」對調（端點停用）；
  **第一層順位＝全校處室的羅列順位**，未來名冊、權限表單等引用單位時即依此順位呈現。
- 表格直接改「層級」時，若原上級不符新層級則**暫留空**，
  由驗證回報「未指定上級單位」擋住儲存，直到補選。

## 介面

頂部控制列（兩種檢視共用）：

- **學校層級數**（1～5）與**各層名稱**。縮小層級數時若仍有單位在更高層 → 拒絕並列出那些單位。
- 檢視切換「表格／視覺化」、**還原**（放棄未存變更）、**儲存變更**（未變更或驗證不過時停用）。
- 驗證訊息即時顯示；未存變更以文字提示。

**A. 表格檢視**（`OrgUnitTable.tsx`，同時是行動裝置與無障礙路徑）

| 欄位 | 行為 |
|---|---|
| 層級 | 下拉 1..N（顯示層名）；改變即連動子樹 |
| 單位名稱 | 直接編輯（≤ 40 字，空白列擋存） |
| 所屬上級單位 | 下拉**只列出上一層**的單位；第 1 層固定「（最上層）」且停用；缺上級時標紅「請選擇上級單位」 |
| 子單位 | 筆數 |
| 操作 | 上移／下移（與同層前後單位對調，端點停用）、＋子單位（已達層級上限則停用）、刪除（有子單位會被擋） |

**B. 視覺化檢視**（`OrgUnitTree.tsx`，第 1 層母艦 + 原生 HTML5 拖曳）

- 以**第 1 層單位為母艦**：每個單位一張卡片，第 2 層卡片巢狀放在母艦內，
  第 3 層以下依此類推（左側縱線表示層級關係）。
- **卡片只顯示單位名稱**（無層名、無上級、無按鈕）；新增、改名、刪除請用表格檢視。
- 拖曳卡片到**另一張卡片**＝設為其下級（連同整棵子樹平移）；
  拖到**最外層虛線空白處**＝設為最上層。
- 禁止拖入自己或後代、禁止使子樹超出層級數（不接受放置，不做任何變更）。
- 放置中的目標以主題色外框提示（`box-shadow`）。
- **行動裝置不支援 HTML5 拖曳**，請改用表格檢視。

兩種檢視共用**同一份未儲存狀態與單一儲存鈕**，切換不會遺失內容。

## 與其他功能的關係

- **單位樹不接權限**：權限表單的處室 badge／整包勾選仍用靜態 `DEPARTMENTS`；
  兩者日後以單位 `code` 串接（例如教職員名冊 `unit` 改為引用單位、按單位授權）。
- **不變項**：超級屬性的層級守門、`settings` 讀寫僅超級、`schoolSettings` 超級專屬、
  `roleEnabled` 身分開關，皆不因本功能改變；`settings/system` 的覆寫行為也未變動。

## 驗收清單

1. 一般管理員看不到「學校基本設定」首頁卡片；直開 `/admin/school-settings` 或
   `/admin/school-settings/org` 顯示「權限不足」；`GET/PUT /api/admin/school/org` 回 403。
2. 調整層級數與各層名稱 → 儲存後重新整理仍在。
3. 表格：新增最上層單位、設上級、改層級（子樹連動）、補選上級後才可儲存；
   「上移／下移」只動同層順位、第一層順序即全校處室順位，首末筆按鈕停用。
4. 拖曳：「教學組」在「教務處」母艦卡片內（第 2 層）；把它拖到「學務處」卡片
   → 巢狀位置跟著移；拖到最外層空白 → 回到第 1 層母艦。
5. 拖入自己的後代 → 無反應；搬移會超出層級數 → 訊息拒絕。
6. 刪除有子單位者 → 訊息拒絕。
7. 縮小層級數但仍有更高層單位 → 拒絕並列出單位名稱。
8. 「儲存變更」後稽核紀錄出現 `school_org_updated`。
9. **存一次「系統設定」不會清掉單位資料**（不同文件）。
