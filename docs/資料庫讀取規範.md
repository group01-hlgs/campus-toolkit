# 資料庫讀取規範（Firestore 讀取鐵律）

本文件為**資料庫讀取的唯一規格來源**。任何新增、修改 Firestore 讀取的程式碼，
改完先對照本文檢查清單。

起因：一次 924 筆的名冊匯入曾把單日讀取量衝到 4.2 萬次，逼近 Spark 方案
**50,000 讀取／日**的免費額度。讀取量不是「效能問題」而已，是會把服務打爆的
**計費與配額問題**。

適用範圍：`src/` 下所有伺服器端 Firestore 存取（Firebase Admin SDK）。
所有讀取都發生在 API route 內，快取與失效皆以伺服器端為準。

---

## 一、計費前提（鐵律為什麼存在）

| 項目 | 計費方式 |
|---|---|
| 查詢（query） | **回傳 1 筆文件 ＝ 1 次讀取**；查無資料的空查詢仍收最低 **1 次** |
| 點查（`doc(id).get()`） | 文件存在＝1 次；**不存在＝0 次** |
| `count()` 聚合 | 每 1,000 筆索引收 1 次（最低 1 次），不回傳文件 |
| 索引讀取 | 查詢最多含 **1 個 range／排序**欄位時不另收索引讀；多欄位複合索引按命中的索引項目另計 |
| 寫入 | 每筆 1 次寫入（本文件重點在讀取，但見「保留不動」一節） |
| 免費額度 | Spark 方案 **50,000 讀／日**，超過後按量計費 |

推論（整份文件的出發點）：

1. **把 10,000 筆撈回來再挑 3 筆** ＝ 10,000 次讀取；**在 Firestore 端 `where` 挑出那 3 筆** ＝ 3 次讀取（＋空查詢最低 1 次的差異）。差距是千倍級的。
2. **`getAll` 不會比逐筆點查便宜**（計費相同，每筆 1 讀）；分塊是為了請求體與逾時上限，不是為了省讀取。
3. **同一份資料在一次請求／短時間內被讀很多次**，是唯一的「無痛浪費」——它既不改善正確性，也不需要動資料。

## 二、六條鐵律

### 鐵律 1：先自問「真的需要讀嗎」

動手寫 `.get()` 之前先依序問：

1. 這筆資料**剛才已經讀過了**嗎？（同請求內復用 → 鐵律 5）
2. 可以**從已有的東西推導**嗎？（例如 session 驗證時已附帶的欄位）
3. 可以**推到 Firestore 端**做嗎？（→ 鐵律 2、3）
4. 可以**延後幾秒再讀**嗎？（→ 鐵律 6）
5. 一定要**現在、用查詢**讀嗎？（能否點查？能否乾脆不讀？）

四個答案都還是「要讀」，才發出查詢。

### 鐵律 2：過濾下推（filter pushdown）

**能寫成 `where` 的條件，一律寫在 Firestore 查詢上**，不接受
「整份撈回來 → 迴圈裡 `.filter()`」。查詢自訂範圍的範例：

```ts
// ✅ 只讀該班（回傳筆數 ≈ 該班人數，不是全校人數）
db.collection(rosterCollection("student"))
  .where("academicYear", "==", period.academicYear)
  .where("semester", "==", period.semester)
  .where("classCode", "==", code)
  .get();

// ❌ 整份當期學生名冊撈回來再挑班級
loadPeriodEntries(period, "student"); // 然後在 JS 裡 filter classCode
```

例外（**刻意保留整表讀取**的情形，見第五節）：
語意無法用查詢表達時（如「缺 `status` 視為有效」），不得用
`where("status", "==", "有效")` 取代整表讀取，改用快取買回延遲。

### 鐵律 3：查詢回傳幾筆 ＝ 幾次讀取——所以要「精準」

**單筆操作只配精準查詢**，不允許為了查一件事把整張表讀進來：

```ts
// ❌ 單筆帳號建立：整表建索引（N ＝ 全站使用者數的讀取）
const index = await loadAccountIndex();

// ✅ 單筆查重：email／account／學號各一筆精準等值查詢（查無＝1 次空查詢）
const conflict = await checkAccountConflictDirect(account, roster, { role, period });
```

- **單筆（表單新增、更新、綁定）** → 一律精準查詢。
- **整批（批次匯入）** → 才允許一次建整表索引，讓整批列攤銷那 1 次掃描。
- `where` 一律配當期條件（`academicYear`＋`semester`）或 `limit`，
  不產生「無界查詢」（沒有範圍條件的整集合查詢）。

### 鐵律 4：循環內禁止逐列查詢（N+1）；批量讀取須分塊

**兩個要求：**

1. **禁止 N+1**：迴圈／批次處理的每一列都發一次查詢是最高危的模式。
   正確作法＝**開頭一次載入所需上下文，之後每列純計算**：

   ```ts
   // ✅ 整批只讀一次「當期管理員名冊＋其使用者帳號」，
   //    之後每列的守門判定全是純計算（lib/roster.ts loadAdminGuardContext）
   const adminGuard = await loadAdminGuardContext();
   for (const row of rows) {
     const msg = countOtherActiveAdminsFrom(adminGuard, row.uid); // 0 讀取
   }
   ```

2. **批量讀取分塊**：`getAll`、批次請求體一律 **200 筆／批**
   （`in` 查詢另有 **30 個值／批**的上限），避免單一請求過大被拒或逾時：

   ```ts
   for (let i = 0; i < uids.length; i += 200) {
     const chunk = uids.slice(i, i + 200);
     const snaps = await db.getAll(...chunk.map((uid) => db.collection(USER_COLLECTION).doc(uid)));
   }
   ```

### 鐵律 5：同請求內復用（一次驗證、一處使用），敏感欄位剝除

- **驗證基線只讀一次**：`verifySession` 讀過的使用者文件、當期名冊條目，
  掛在回傳值上（`VerifiedSession` 的 `__user`／`__entry`）供同請求後續復用；
  禁止「驗證讀一次、要用再讀一次」。呼叫端採用 `adminEntryOf()`、
  `hasAdminModule()` 等 helper 即自動復用。
- **回應前剝除**：`__user`／`__entry`（含 `passwordHash` 等）**不得**出現在任何
  回應或 log，API route 解構時逐一剝除（見 `api/auth/me`）。
- 同一請求內的其他重複讀取（period、設定、守門）同理：**讀一次、往下傳**。

### 鐵律 6：短 TTL 快取 ＋ 寫後失效

清單、總覽這類「重新算一次要幾千次讀取」的結果，用 `cachedRead` 快取：

```ts
import { cachedRead, invalidateReadCache } from "@/lib/read-cache";

const payload = await cachedRead(
  `admin:roster-list:${role}:${period.academicYear}:${period.semester}`,
  15_000, // TTL：使用者可接受的最短資料延遲
  async () => { /* 真正的查詢 */ }
);
```

- **任何資料變更（增修刪）成功後，呼叫 `invalidateReadCache()`**（全部清除即可，
  快取量小）；設定類文件另見 `invalidateSettingsCache()`。
- **陳舊性上限**：同程序＝TTL；跨程序（serverless 多實例）**無法互相通知**，
  陳舊上限同樣是 TTL——這就是 TTL 取 10～30 秒而不是幾分鐘的原因。
- 讀失敗不寫入快取，直接拋錯；併發同 key 請求共用同一次載入。

## 三、各類資料的讀法（照抄即可）

| 情境 | 做法 | 實作位置 |
|---|---|---|
| 每請求驗證基線 | `verifySession` → `VerifiedSession`（`__user`/`__entry` 復用） | `src/lib/dal.ts` |
| 設定系統文件 | `readSystemDoc()` 快取；寫入後 `invalidateSettingsCache()` | `src/lib/settings-server.ts` |
| 班級／校務設定文件 | `cachedRead("setting-doc:…", 30s)` | `api/admin/classes` |
| 名冊清單 | `where(academicYear,semester)` ＋ `cachedRead(15s)`；帳號欄 `getAll` 200/批 | `api/admin/roster` |
| 帳號工作表 | 整表 `get()` ＋ `cachedRead(15s)` | `api/admin/accounts` |
| 班級總覽 | 單班模式 `where(classCode)` 下推；總覽 `cachedRead(30s)` | `api/admin/classes` |
| 批次守門（最後一位管理員／超級） | `loadAdminGuardContext()` 一次 ＋ `*From()` 純計算 | `src/lib/roster.ts` |
| 單筆查重 | `checkAccountConflictDirect()` 精準查詢 | `src/lib/roster.ts` |
| 批次匯入查重 | 一次 `loadAccountIndex()`/`loadRosterIndex()` 攤銷 | 批次 routes |
| 批次刪除名冊範圍 | `where("uid","in",chunk)`＋當期條件下推（不再整表掃） | `api/admin/accounts/batch` |
| 改掛名冊條目 | `targetRef.create()` 撞到 `already-exists` 即跳過（免先 `get()` 判存在） | `src/lib/roster.ts` |

**失效鉤子**（資料變更成功後必須 `invalidateReadCache()`）：
`api/admin/roster`、`api/admin/roster/batch`、`api/admin/roster/link`、
`api/admin/accounts`、`api/admin/accounts/batch`、`api/admin/school/classes`、
`api/admin/school/profile`。新增會改動名冊、帳號、班級、校務資料的路由時，
**記得補上**。

**TTL 基準**：清單類 15 秒；總覽／設定文件 30 秒。要在「即時性」與「讀取量」間
取捨時，以 15～30 秒為安全帶。

## 四、索引注意事項

- 純 `where` **等值**查詢（含 `academicYear`＋`semester`、`uid in […]` 與
  其他等值條件的組合）**沿用現有模式即可，不需要複合索引**
  （Firestore 以合併連接多個單欄位索引執行）。
- 若部署後查詢回 `FAILED_PRECONDITION`，**照錯誤訊息裡的連結建立該複合索引**，
  不要改回「撈回來再篩」。
- `in`／`not-in` 比較值上限 **30 個**（分塊常數 `IN_CHUNK = 30`）。
- 查詢若需要 `orderBy`，注意「超過 1 個 range 欄位」會開始收索引讀取。

## 五、刻意保留、不要「優化」掉的模式

| 模式 | 保留理由 |
|---|---|
| 變更（mutation）後 refetch 清單 | **正確性優先**：畫面上的資料必須反映剛寫入的結果，省這幾次讀取不值得 |
| `keepalive` 的請求 | 於頁面卸載時送出（登出等），移除會丟失操作 |
| `classes` 總覽讀整份當期名冊 | 「缺 `status` 視為有效」的語意無法用 `where(status)` 表達（查不到就等於有效），只能整表讀＋快取 |
| 批次匯入開頭的一次整表索引 | 一整批列攤銷 1 次掃描，遠低於每列查一次 |
| `getCurrentPeriod()` 等每請求 1～2 讀 | 已由 `readSystemDoc`／快取吸收；再壓縮會犧牲正確性 |
| 目前無 `onSnapshot`、無輪詢 | 不存在即不存在；**不要新增**常駐即時監聽（每 listener 都是持續的讀取來源） |

## 六、交付前檢查清單

新增／修改任何 Firestore 讀取時，逐項確認：

- [ ] 有 `where` 能表達的條件，**沒有**撈回來再 `filter`（鐵律 2）
- [ ] 單筆操作沒有整表掃描；整批才允許一次建索引（鐵律 3）
- [ ] 迴圈／批次內**沒有**逐列 `.get()`／查詢（N+1）；上下文開頭讀一次（鐵律 4）
- [ ] `getAll`／請求體有分塊（200/批）；`in` 不超過 30 值（鐵律 4）
- [ ] 讀過的資料同請求內復用；回應不含 `passwordHash` 等敏感欄位（鐵律 5）
- [ ] 清單／總覽類有 `cachedRead`，**變更路徑有 `invalidateReadCache()`**（鐵律 6）
- [ ] TTL 落在 10～30 秒；知道跨程序陳舊上限＝TTL
- [ ] 沒有新增無界查詢（無 `where`、無 `limit` 的整集合讀取）
- [ ] 沒有新增 `onSnapshot`／輪詢
- [ ] `npm run lint` 通過
