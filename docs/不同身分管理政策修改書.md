# 不同身分管理政策修改書

> 狀態：規劃中（尚未進入實作）
> 相關專案：A 主程式（campus-toolkit）／B 模組市集／C examRegistration
> 前置討論：功能模組四身分權限收縮方案（2026-10-20）

---

## 1. 背景與動機

現行「功能模組管理」採雙層權限結構：

1. **入口功能層**：每個功能模組對四種身分（學生／家長／教職員／管理員）各有「提供」與「入口功能」勾選，控制各身分是否看得到該模組的使用者端入口。
2. **管理端權限層**：管理員名冊條目（`rosterAdmins`）以 `attribute`（超級／一般）＋`modules[]`（指定功能模組清單）決定管理員帳號可用哪些管理頁。

此結構衍生三個問題：

- **其他三身分無法被指定管理功能模組**：教職員／家長／學生若需管理某模組（例如學務主任管理升學考試報名），必須先建立「管理員」名冊條目並掛上模組指派——多出一條冗餘身分，且該帳號會同時具備管理員身分的所有可見入口。
- **管理員入口逐模組勾選多餘**：管理員本職即為系統管理者，對所有功能模組的管理權應為預設，不需於 `/admin/modules` 逐列勾選「入口功能」。
- **超級／一般層級過重**：一般管理員連「功能模組管理」本身都無法操作，學校場景（管理員通常 1–3 人）此區分收益低、維運成本高。

## 2. 修訂目標

| # | 目標 | 說明 |
|---|------|------|
| G1 | 管理員恆全權 | 管理員對所有功能模組預設擁有管理權，移除管理頁「管理員」欄與逐模組入口勾選 |
| G2 | 取消管理員屬性區分 | 管理員名冊條目不再區分超級／一般，就是「管理員」 |
| G3 | 指定非管理員管理者 | 管理員可指定「該學期」其他三身分的帳號，管理特定功能模組；被指定者無需管理員名冊條目 |
| G4 | 模組內子權限 | 被指定者的管理權可細分到模組內各項操作（子權限），由模組作者於 manifest 宣告 |

## 3. 現行模型摘要（修改基準）

### 3.1 雙層權限結構

| 層級 | 資料來源 | 落點 | 判定 |
|------|----------|------|------|
| 入口功能 | manifest `provides` / `defaultRoleEnabled` | `settings/system.featureModuleRoles`（Firestore） | 各身分使用者端入口是否顯示 |
| 管理端權限 | `rosterAdmins` 條目 `attribute` + `modules[]` | Firestore `rosterAdmins` | 管理員帳號可用哪些管理頁 |

### 3.2 現行授予規則（`adminModulesOf`，`lib/roster.ts`）

- `attribute === "超級"`：全開（含 `superOnly`）。
- `attribute === "一般"`：`BASE_ADMIN_MODULES`（core）＋ `modules[]` 指派，且強制剝除 `superOnly`。
- `superOnly` 模組：`schoolSettings`、`miscSettings`、`modules`、`themeMarket`、`stats`。

### 3.3 現行守門

- API：`requireAdminModule(module)` → 需當期 `rosterAdmins` 條目，且 `adminModulesOf` 含該模組。
- 超級判定：`isSuperAdmin(session)` → `entry.attribute === "超級"`。
- 功能模組管理頁：僅超級可操作開關。

## 4. 目標模型

### 4.1 新雙層結構

| 層級 | 決定者 | 內容 |
|------|--------|------|
| **入口功能層**（不變） | 超級管理員→改為全體管理員 | 學生／家長／教職員三身分的「提供／入口功能」；**移除管理員欄** |
| **管理權層**（重構） | 管理員指派 | 管理員恆全權；其他三身分由管理員按學期指定帳號＋子權限 |

### 4.2 管理權授予規則（新）

```
判定 session 對模組 M 之管理權：
1. session.role === "admin"
   → 全權（不看子權限、不受指派限制）
2. 否則，取當期該身分名冊條目 entry.managedModules
   → 找 module === M 之項目
   → 有項目：取得 permissions（子權限碼陣列）
   → 無項目：無管理權
```

### 4.3 指定機制

- **指定者**：任何管理員（全體平等）。
- **被指定者**：當期身分名冊（`rosterStudents` / `rosterParents` / `rosterStaff`）中之帳號。
- **期間**：綁定名冊條目所屬學年學期——學期切換後新條目需重新指定，與「該學期」語意一致。
- **失效**：帳號被移出名冊、條目停用或學期結束 → 自動喪失資格，無需額外清理。

### 4.4 安全邊界

- 取消超級／一般後，全體管理員可操作所有管理頁（含系統設定、功能模組管理、主題市集、統計、管理其他管理員）。
- 僅保留守門：
  1. **最後一位管理員不可停用／刪除**（沿用現行）。
  2. 不可變更自己為停用（沿用現行意圖）。
- `superOnly` scope 於管理員路徑不再剝除（全員可及）；`core`／`assignable`／`superOnly` 三分仍保留於註冊表，供文件與 UI 分組用。

## 5. 六點決議

### 決議一：管理範圍與入口——沿用 `/admin/*`，放寬角色閘門

- 被指定者以原身分（教職員／家長／學生）登入，直接存取 `/admin/<模組>` 管理頁；不為每身分重做管理 UI。
- 守門由 `requireAdminModule(M)` 改為 `requireModulePermission(M, action?)`：
  1. `role === "admin"` → 放行。
  2. 非管理員 → 查 `managedModules`；若呼叫時帶子權限碼則需包含之。
- 導覽入口：被指定者之儀表板／導覽列自動出現該模組管理入口（判定同上）。
- `/admin` 外殼（`AdminSectionShell`）之角色閘門改為「管理員或持有任一模組指派」。

### 決議二：安全邊界——管理員平等全開

- `attribute` 欄位：UI 移除、API 停止寫入；Firestore 欄位保留一個版本週期後清理（讀取時忽略）。
- `adminModulesOf()` 簡化為：管理員條目存在 → 回全量 `ADMIN_MODULE_VALUES`。
- `checkAdminAttribute` 收斂為僅守「最後一位管理員」。
- 「功能模組管理」頁操作權限：由「僅超級」改為「全體管理員」。
- 層級需求以「指定管理員」機制替代：不想給全權者，不建立管理員條目，改用模組級＋子權限指派。

### 決議三：指定介面與資料落點——名冊條目為主、`/admin/modules` 為介面

- **資料落點**：三張身分名冊條目新增 `managedModules` 欄位（詳見 §6）。
- **主介面**：`/admin/modules` 每列展開「管理人員」區塊：
  1. 依身分篩選搜尋當期名冊帳號。
  2. 加入 → 顯示該模組 `managerPermissions` 勾選清單。
  3. 儲存 → 寫入該人名冊條目。
  4. 列表顯示已指定者＋子權限摘要，可編輯／移除。
- **輔介面**：身分名冊管理頁、使用者帳號頁提供檢視／編輯（同份資料，避免雙頭管理）。
- Excel 批次：名冊批次匯入格式新增 `指定功能模組` 欄（格式：`examRegistration:viewRoster+approve;...`），供批次指派。

### 決議四：入口功能表格——只移除管理員欄

- 學生／家長／教職員三欄「提供／入口功能」完全不變（控制使用者端入口）。
- 移除管理員欄；`provides.admin`、`defaultRoleEnabled.admin`、`featureModuleRoles.admin` 自型別與資料面退役。
- `build-module-registry.mjs` 對 `provides.admin` 之驗證改為「不得宣告」（或忽略既有值）。

### 決議五：既有資料遷移

| 既有資料 | 遷移動作 |
|----------|----------|
| `rosterAdmins.attribute`（超級／一般） | 一律保留有效管理員條目；欄位停止讀取，一個版本週期後清理 |
| 管理員條目 `modules[]` | 廢棄（管理員恆全權）；欄位保留但不再使用 |
| 以「管理員條目＋modules」間接管理之**非管理員**帳號 | 無法自動轉換 → 遷移時產出待辦清單（CSV／稽核紀錄），由管理員在 `/admin/modules` 重新指定至對應身分名冊 |
| `settings/system.featureModuleRoles` 之 `.admin` 鍵 | 停止讀取與寫入；既有值忽略 |

遷移執行方式：一次性腳本（`scripts/migrate-module-managers.mjs`）＋稽核記錄，或併入版本升級流程；執行前備份 `rosterAdmins` 集合。

### 決議六：一帳號多身分——管理員恆全權、指派僅對非管理員身分生效

- 判定順序固定：`role === "admin"` → 全放行；否則套用當前身分條目之 `managedModules`。
- 帳號切換至教職員／家長／學生視角時，才套用該身分之指派——管理員可切換身分體驗被指定者介面，無需額外處理。

## 6. 資料模型變更

### 6.1 身分名冊條目新增欄位

適用：`rosterStudents`、`rosterParents`、`rosterStaff`（`rosterAdmins` 不適用——管理員恆全權）。

```ts
// src/types/roster.ts
export interface ManagedModuleGrant {
  /** 權限單位代碼（同 ModuleMeta.value，如 "examRegistration"） */
  module: string;
  /** 子權限碼陣列（來源模組 manifest 之 managerPermissions） */
  permissions: string[];
}

export interface RosterEntryBase {
  // ...既有欄位
  /** 被指定管理之功能模組（選填；僅非管理員身分名冊使用） */
  managedModules?: ManagedModuleGrant[];
}
```

- 欄位缺省＝未被指定（fail-safe 與現行風格一致）。
- `permissions` 為空陣列＝可進管理頁但無任何子操作權（唯讀入口）；是否允許此狀態由 UI 決定（建議至少勾一項）。

### 6.2 `rosterAdmins` 欄位退役

```ts
// 讀取時忽略，寫入時停止
attribute?: string;   // 退役
modules?: string[];   // 退役
```

`ROSTER_ENTRY_FIELDS.admin` 由 `["attribute", "modules"]` 改為 `[]`（或僅保留顯示用之唯讀註記）。

### 6.3 `settings/system` 欄位

```ts
featureModuleRoles: Record<string, Record<UserRole, boolean>>
// UserRole 之 admin 鍵停止讀取與寫入；型別改為 Partial<Record<Exclude<UserRole, "admin">, boolean>>
```

### 6.4 manifest contract 擴充

```jsonc
// module.json
{
  // ...既有欄位
  "permission": { "mode": "new", "value": "examRegistration", "category": "校務資料" },
  // 新增：非管理員管理者之子權限宣告（選填；未宣告＝指派時無子權限可勾，僅管理員可完整管理）
  "managerPermissions": [
    { "value": "viewRoster",  "label": "查看報名名冊" },
    { "value": "approve",     "label": "審核報名" },
    { "value": "export",      "label": "匯出資料" },
    { "value": "configure",   "label": "設定考試場次" },
    { "value": "broadcast",   "label": "發送家長公告" }
  ]
}
```

- `build-module-registry.mjs` 驗證：`managerPermissions` 若存在，每項需有非空 `value`（蛇形或 camel 碼）與 `label`；`value` 不得與內建權限碼衝突。
- 產生檔擴充：`feature-modules.generated.ts` 或 `modules.generated.ts` 帶出 `managerPermissions`，供 `/admin/modules` UI 勾選清單使用。
- contractVersion 判定：宿主端依 `managerPermissions` 欄位有無做相容（無此欄位之舊模組＝不開放非管理員指派）。

## 7. 守門 API 變更（`lib/dal.ts`）

### 7.1 簡化

```ts
// adminModulesOf：管理員條目存在即全量
export function adminModulesOf(entry) {
  if (!entry) return [];
  return [...ADMIN_MODULE_VALUES];
}

// isSuperAdmin：退役或改名為「是否管理員」語意
// requireSuperAdmin：退役（原 superOnly 閘門改為 requireAdminModule）
```

### 7.2 新增

```ts
/** 取得非管理員身分對模組 M 之子權限（無條目或非管理員身分回 []） */
export function modulePermissionsOf(
  session: SessionPayload,
  module: string
): string[] | null;  // null = 無任何指派；[] = 有指派但無子權限；[...] = 子權限清單

/** 守門：管理員恆過；非管理員需 managedModules 含模組（及可選子權限） */
export async function requireModulePermission(
  module: string,
  permission?: string
): Promise<ModulePermissionContext>;
// 回傳 { kind: "admin" } | { kind: "delegated", permissions: string[] }
```

### 7.3 模組端替換

| 現行 | 目標 |
|------|------|
| `requireAdminModule("examRegistration")` | `requireModulePermission("examRegistration")`（頁面級） |
| 同上（寫入動作） | `requireModulePermission("examRegistration", "approve")`（動作級） |
| `isSuperAdmin(session)` 決定開關可否操作 | `session.role === "admin"` 或移除該限制 |

### 7.4 session 回傳（`/api/auth/me`）

```ts
{
  // ...既有
  adminAttribute?: never;          // 退役
  adminModules?: AdminModule[];    // 管理員恆全量；非管理員回 []
  delegatedModules?: Array<{       // 新增：當前非管理員身分之指派
    module: string;
    permissions: string[];
  }>;
}
```

## 8. UI 變更

### 8.1 `/admin/modules` 功能模組管理頁

| 區塊 | 變更 |
|------|------|
| 表頭 | 移除「管理員」欄；保留學生／家長／教職員 |
| 身分欄 `RoleCells` | 迭代 `ALL_ROLES.filter(r => r !== "admin")` |
| 操作權限 | 所有開關／checkbox 由「僅超級」改為「全體管理員」（即登入 `/admin` 即可操作） |
| 選用模組列 | 新增展開區「管理人員」：搜尋名冊 → 加入 → 勾子權限 → 列表管理 |
| 底部說明 | 「管理端權限（指定功能模組）說明」改寫為新政策（管理員恆全權＋指定制） |

### 8.2 身分名冊管理頁（`/admin/roster`）

- 管理員分頁：移除「屬性」下拉（超級／一般）、「指定功能模組」勾選區。
- 學生／家長／教職員分頁：條目編輯增加「管理功能模組」區（同 `/admin/modules` 之指定 UI，或唯讀摘要＋連結至模組頁編輯）。

### 8.3 使用者帳號頁（`/admin/accounts`）

- 建立／編輯帳號時之管理員區塊：移除屬性與模組指派。
- 各身分區塊：顯示被指派之功能模組（若有）。

### 8.4 被指定者端

- 儀表板／導覽：依 `delegatedModules` 顯示管理入口卡片。
- `/admin` 外殼：放寬為「管理員或持有任一指派」可進入；僅渲染有權限之區塊。

## 9. 對 C（examRegistration）之影響

C 需配合修改（待 A 端 contract 完成後排程）：

1. `module.json`：新增 `managerPermissions` 宣告（§6.4 範例）；contractVersion 視需要 bump。
2. API：`/api/admin/exam-registration/*` 各路由由 `requireAdminModule` 改為 `requireModulePermission("examRegistration", "<子權限>")`。
3. 頁面：`/admin/exam-registration*` 依回傳之權限上下文控制按鈕／區塊顯示。
4. 版本：`minHostVersion` 需對齊 A 支援 `managerPermissions` 之版本。

B（模組市集）無結構性變更；新 contract 之模組上架後市集僅需正確顯示版本相容性。

## 11. 開放問題（P0 前需確認）

1. **子權限碼風格**：建議 camelCase（`viewRoster`），與現行模組 value 風格一致？或蛇形？
2. **「有指派但子權限為空」**：是否允許（僅入口無操作），或 UI 強制至少一項？
3. **家長／學生被指定管理**：是否限制可指派之模組種類（例如僅限 `provides` 對該身分為 true 者），或不設限？
4. **批次匯入格式**：`指定功能模組` 欄之字串格式是否採 `module:perm1+perm2;module2:perm3`？
5. **`featureModuleRoles.admin` 清理時點**：與 `attribute` 同步（一個版本週期）或立即？
